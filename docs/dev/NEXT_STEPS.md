## Windows without mandatory WSL

Shipped in 0.6.0. Order and decisions are in the vault's `feat and bugs.md`: PowerShell 5.1 is the first native shell; new installs default to it, existing users keep WSL.

- Step 1 in source (2026-11-03): the daemon no longer checks WSL at startup (`launch::check_system`), so it starts on a PC without WSL; a WSL pane checks WSL when it launches. Setup no longer refuses to install without WSL; its doctor reports only an installed-but-broken WSL (WSL 1 default, guest not starting), not a missing one. WSL errors now say what to run (`wsl --install`, `wsl --set-version NAME 2`) instead of "Compi requires WSL2" or a bare "file not found". Not yet seen on a PC without WSL: the first tab there still fails (dimmed, reason only in Diagnostics) until native PowerShell panes exist.
- Step 2 in source (2026-11-03), daemon protocol 36: one global shell setting, `[shell] windows = "powershell" | "wsl"` and Settings → Terminal → Shell (Windows only). `LaunchProfile::windows_shell` carries it; the Windows daemon starts `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoLogo` through ConPTY in the requested Windows folder (`/mnt/c/x` and `/C:/x` translated, Linux-only folders → `%USERPROFILE%`), with `COMPI_SURFACE_ID`, `COMPI_INSTANCE`, `COMPI_CLI`, `COMPI_DATA_DIR` in its environment. A restart keeps the shell's stored kind; new tabs and splits follow the setting. The app and CLI write the setting once (`config::settle_windows_shell`): WSL when client window state already exists, else PowerShell. Native panes report environment kind `windows`. Seen through a disposable instance: Windows PowerShell 5.1 at `C:\Users\johns`, `/mnt/c/...` and `C:\Windows` folders, a Linux folder falling back home, WSL zsh after switching, and a split following the new setting. Not yet seen: the Settings row on screen. Release prep must move the five pinned protocol numbers to 36 (RELEASE-FLOW step 3).
- Step 3 in source (2026-11-03): the PowerShell bridge, `assets/compi-shell.ps1`, passed as `-NoExit -EncodedCommand` (not subject to the script execution policy) after the user's profile. It puts `COMPI_CLI`'s folder first on `PATH` and wraps the profile's `prompt`: once `OSC 777;compi;pid`, then OSC 7 as `file://localhost/C:/…` (segments percent-encoded; non-drive locations unreported) and `OSC 133;A;aid=$PID`, then the original prompt with `$?` and `$LASTEXITCODE` restored. Metadata runs Git in `C:/…` for those reports; lost-shell resume checks the Windows folder. - Step 4 in source (2026-11-04): Settings → Terminal → Starting folder over the existing `[shell] working_directory`: **Choose…** (native folder picker), **Home** (removes the key), shared with every window like the shell setting (`share_launch_change`). - Step 5 in source (2026-11-04): PowerShell panes get the host. `SurfaceInfo::runs_powershell`. Daemon: `ListDirectory`/`SearchDirectory` from a PowerShell surface use the Windows host (`DirectoryPlace::WindowsHost`, `file_tree::{list_host_directory, search_host_files}`, results joined with `\`); Windows metadata names the foreground process from the shell's newest child (Toolhelp, by the bridge-reported pid), else the shell itself, so tab names show it and Fetch/Pull/Push can find an idle PowerShell. ## Font size

## Going anywhere from either shell (0.6.1)

In source (2026-11-05, no protocol or workspace-format change):

- PowerShell bridge (`assets/compi-shell.ps1`): `cd` is aliased to `__compi_cd` unless the profile already changed it (zoxide's `cd` stays). A single path argument PowerShell cannot find goes through `__compi_other_side`: `/mnt/<d>/x` and `/C:/x` to the drive; `~`, `~/x` and `/x` in the default WSL distribution (registry `Lxss`, home from its `/etc/passwd`, cached once found); a relative path typed at the Windows home in the Linux home. Linux paths resolve through `wsl.exe … wslpath -a -w`, which follows links (`~/proj` → `/mnt/c/…` lands in `C:\…`), else `\\wsl.localhost\<distribution>\…`; `$LASTEXITCODE` is kept. `compi z`/`jump`/`tree` are a function now: OSC 7, then `777;compi;jump|tree`, the base64 reply read with `ReadKey` (no echo), and the same translation; other `compi` commands run `$env:COMPI_CLI`, with pipeline input forwarded.
- Bash/Zsh bridge: inside WSL a `cd` function (defined before the rc, so a user's wins; not exported to login Bash) translates `C:\x`, `C:/x`, `/C:/x` through `wslpath -u` and `\\wsl.localhost\<this distribution>\x` / `\\wsl$\…` to `/x` when Bash cannot find the path, and says to quote or use `/` for `C:Users…` (backslashes the shell removed). `_compi_cd_target` is shared with `_compi_choose_directory` and exported for login Bash.
- Launch: `wsl::resolve_launch` takes `/C:/x` as `C:\x` and opens the Windows home itself (`USERPROFILE`, any separator or case; not `/mnt/c/Users/me`) at `~`. `resolve_powershell` opens a Linux folder as `windows_path_for_wsl` names it (was always `%USERPROFILE%`). The palette's **Jump to project** still opens a new tab (a focused shell may be running a program), which now lands in the folder in either shell.
- Explorer (`compi_client::explorer`): an installed Compi (root with `Compi-Setup.exe`) writes the Open with / Open in Compi entries `Compi.wxs` writes, on a background thread at start, when they are missing or point elsewhere; Setup's removal deletes them. A unit test keeps the list equal to `Compi.wxs`.
- `cargo dev` rebuilds the daemon for `assets/compi-shell.ps1` and `assets/compi-monitor.sh`, which it embeds (only `compi-shell.sh` before).
- Checked in `cargo dev` on Windows: PowerShell `cd ~/proj/compi` and `cd proj/compi` from home landed in `C:\Users\johns\OneDrive\Desktop\Proj\compi` with `$LASTEXITCODE` kept, `cd /home/thatmfer` in `\\wsl.localhost\Ubuntu\home\thatmfer`, `/mnt/c/Windows` and `/C:/Users` on the drive, `C:\nope` still an error; WSL `cd 'C:\Users\johns'`, `cd C:/Windows`, `cd /C:/Users` under `/mnt/c`, `cd C:Users` with the hint; Bash and Zsh translation cases; `compi z` in PowerShell opened Jump to project with both sides' folders, and a reply of `/home/thatmfer/proj/compi/crates` changed to `C:\…\compi\crates`; new tabs: PowerShell at `/home/thatmfer/proj/compi` → `C:\…\compi`, WSL at `C:\Users\johns` → `/home/thatmfer`, at `C:\Users\johns\Desktop` → `/mnt/c/Users/johns/Desktop`; the explorer entries removed then restored for the real install root, and one deleted `.png` entry restored. ## Tab groups

In source (2026-11-06, **protocol 37, workspace format 9**; the release pins in `RELEASE-FLOW.md` still say 36):

- Protocol: `WorkspaceSession::groups` (`TabGroup { id, name, color, folded }`, `TabGroupColor` from the theme's ANSI colours, grey from muted text), `WorkspaceTab::group`, `MergedTab::group`; `MoveTab` takes a `TabPlacement` (`Infer`, `Join`, `Leave`); `CreateTabGroup`, `SetTabGroup`, `UpdateTabGroup`, `MoveTabGroup`, `Ungroup`, `RemoveTabGroup`. Folding lives in the daemon, so every window follows it.
- Daemon: `settle_groups` after every mutation and finished removal keeps a group's tabs together at its first tab and drops empty groups; `validate` refuses split, empty or foreign groups. Closing a group queues one `RemovalTarget::Tab` per tab, so format-8 daemons still parse a pending removal. Merges remember each source's group; detached panes inherit theirs. Format 8 → 9 is a relabel; a format-8 daemon reaches its version check on a file with groups.
- Client: the strip is laid out once per frame (`tab_groups.rs`, `CompiApp::tab_strip`) with content-width labels, and every hit test (drop slots, pane drags over the bar, scroll-to-tab) uses those ranges instead of `tab_width` arithmetic. A tab dropped inside a group's span joins it, outside leaves; on a folded label joins at its end; a dragged label moves the group whole. A window whose selected tab gets folded selects the nearest shown tab; picking a folded tab unfolds its group. Commands `group_tab` (Ctrl/Cmd+Shift+G, chooser then name), `remove_tab_from_group`, `rename_tab_group`, `toggle_tab_group_fold`, `ungroup_tab_group`, `close_tab_group`, `move_tab_group_to_new_window`; the transfer takes a list of tabs and needs attached views only for the tab shown in the source.
- CLI: `tab group`, `tab group --into`, `tab ungroup`, and `group list|rename|color|fold|unfold|move|ungroup|close`.
- Checked in `cargo dev` on Windows (posted input, CLI): groups from the CLI, the tab menu's **Add to group ›** and **Add tab to group…** with the name dialog; labels and colour lines drawn; label click folds and unfolds (count shown); Colour submenu; folding the selected tab's group moved the selection right; `tab focus` on a folded tab unfolded it; dragging a label, a tab onto a folded label (joined) and a tab out past the strip's end (left; the emptied group went); **Move tab group to new window** opened a window with exactly the group's three tabs (first try failed: only the shown tab has attached views; fixed); `group close` refused with a running shell when piped (exit 4) and closed exited ones; groups survived a dev daemon restart. Not seen: physical Ctrl+Shift+G, the palette's group context, a label dragged out of the window, macOS.

4. **Scrolling in TUIs and omp.** Scrolling up while a program prints keeps snapping back to the bottom.
   - Causes, measured on a Mac in `cargo dev`: scrollback is capped by 1 MiB of cell memory (`MAX_SCROLLBACK_BYTES`, about 33 bytes a cell), not the 10,000-line setting, so an 80-column pane keeps 420 of 3,000 printed lines and wider panes fewer. Once full, every new line evicts the oldest, the client sees a history that no longer starts with its old one and resets to the bottom (`gui/workspace.rs` `history_invalidated`). omp and Pi clear and reprint the scrollback (`ESC[2J ESC[H ESC[3J`) whenever something above the screen changes, which does the same. Each scrollback change resends the whole history (`terminal/mod.rs`, `Delta.scrollback`). In the alternate screen without mouse reporting (`less`, `man`, Git's pager) the wheel does nothing, and every trackpad event moves at least a line or sends a whole wheel click, with fractions never added up.
   - **Step 1, done in source for 0.2.1; no protocol-version change.** Text-and-neighbour anchors keep the reading row through eviction and clear/reprint, ignoring style changes. Split clear/reprint frames retain only the reading viewport for a 250 ms grace period; a real clear then returns to live output. Uncertain selections are cleared. A "↓ N new lines" chip returns to the bottom when clicked; typing does too. Per-pane fractional deltas produce only whole local scroll lines, mouse reports or alternate-screen arrows. DECSET 1007 defaults on in the daemon; an optional, backward-compatible JSON Input marker distinguishes synthesized arrows from real keys without changing the binary screen layout. Physical wheel/trackpad and Windows/WSL qualification are still open.
   - **Done in source 2026-10-20, step 2 (protocol 30).** History rows are kept compactly on both sides (`HistoryRow`: text, per-cell lengths only for wide or multi-byte cells, style runs, trailing blanks dropped). Deltas carry `Append { evicted, rows }`, or `Replace` on a real clear, RIS, a column resize that rewraps or a burst larger than the history; the client follows appends arithmetically and expands only rows it shows. The 1 MiB cap is replaced by `scrollback_lines × 512` bytes, measured at 10,000 lines × 80 columns: plain text 1.6 MB, colored output 3.2 MB, wide CJK 5.1 MB, all 10,000 lines kept. One appended line now costs 80–280 bytes of history on the wire instead of the whole history (about 11 MB at 10,000 lines before). In `cargo dev`, 12,000 printed lines left lines 1,979–12,000 in the pane (10,000 history plus the screen) where about 420 survived before. RIS now keeps the configured limits. See [Completed work](COMPLETED.md#scrolling-step-2-protocol-30--2026-10-20).
   - Step-1 verification done on macOS: 612 workspace tests passed, all-target Clippy with `-D warnings` passed, and engine/live `cargo dev` smoke confirmed eviction/redraw anchoring and fractional scrolling in real `less`.
   - Windows/WSL visual smoke (2026-10-20): after 12,000 printed lines, a synthetic wheel scroll held reading row 11869 while output continued and the new-lines chip grew from 5 to 96. Resizing exposed another bottom reset: geometry changes bypassed the text anchor. Geometry updates now keep the reading offset and use replacement-history anchoring; uncertain selections still clear. After the fix, reading row 11941 remained at the top through 1800 → 2100 → 1800 physical-pixel window widths during output, with the chip growing 21 → 68 → 94.    - **Resize with a program that rewraps its own text (omp), 2026-10-23, in source.** Reported: after releasing a window drag or picking a snap size, the view jumped to the bottom and stayed there. Cause: omp reprints its transcript wrapped to the new width, so no row of the new history equals the reading row, and the exact-row anchor gave up; a size change also dropped the clear/reprint grace period.
