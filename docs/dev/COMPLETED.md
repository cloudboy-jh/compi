### Native agent chat

Decided 2026-11-08: Compi speaks ACP (Agent Client Protocol, JSON-RPC 2.0 over stdio) to `omp acp`, not OMP's own `--mode rpc`, so OpenCode, Codex and Claude Code (through their ACP adapters) need no second integration; the daemon owns the agent process, like a shell, so a turn survives closing the window or flipping to the terminal.

Phase 1, look first (2026-11-08, omp 18.18.0, throwaway Python driver, nothing in source):

- Start: `omp acp` answers `initialize` in about 2 s. Advertises `loadSession`, `sessionCapabilities` `list`/`fork`/`resume`/`close`, images and embedded context in prompts, MCP over HTTP/SSE, and `_meta.steering`. One auth method (`agent`: credentials already under `~/.omp`), so Compi never handles keys.
- `session/new { cwd, mcpServers: [] }` returns `configOptions`: `mode` (Default, Plan), `model` (838 choices here, current one marked) and `thinking` (`thought_level`, 7 levels). These are the composer's pickers as-is; `config_option_update` arrives at each turn.
- A turn: `session/prompt` streams `agent_message_chunk` (Markdown text), `agent_thought_chunk`, `tool_call`/`tool_call_update` (`kind` read/edit/execute/other, `title`, `status` pending → in_progress → completed/failed, `rawInput`, `content`, `locations`), `usage_update` (`used`/`size` context tokens, cost in USD), `session_info_update`, `available_commands_update` (slash commands); the reply ends with `stopReason` and token counts.
- Edits: the `edit` tool sends `{ type: "diff", path, oldText, newText }`, enough for Compi's diff without Git. `write` sends text only ("Successfully wrote 91 bytes").
- Permissions: `bash` asks through `session/request_permission` (Allow once, Always allow, Reject, Always reject) before its `tool_call` notification arrives, so the card has to show the request's own `toolCall`. Reads and plain edits did not ask under the default approval mode. Per-session yolo is not in ACP; it needs `omp acp --approval-mode …` per process.
- Questions: OMP's `ask` arrives as `elicitation/create` (`mode: "form"`, a JSON schema: `oneOf` choices plus a `<id>__other` free-text field) when the client advertises `elicitation: { form: {} }`; without it, defaults are used. Filling the free-text field overrides the choice, so the card sends only one of them.
- Files: with `fs.readTextFile`/`writeTextFile` advertised, OMP reads and writes through the client (`fs/read_text_file`, `fs/write_text_file`), so Compi would see every write and could serve unsaved editor buffers. Paths are the agent's own: Linux paths from WSL `omp`, `C:\…` from `omp.exe`.
- Cancel: `session/cancel` during a running `sleep 30` returned `stopReason: "cancelled"` within a second; the tool call got no final update, so the UI marks open calls as stopped itself. The next prompt in the same session worked.
- Sessions: OMP saves ACP sessions in its usual store (`~/.omp/agent/sessions/<cwd>/…jsonl`). `session/list { cwd }` lists them with `updatedAt` and message counts; `session/load` replays the whole history as `session/update`s (user chunks, tool calls, replies) before answering; `omp -p --resume <id>` continued an ACP-made session, so chat and TUI share sessions both ways. No session titles over ACP (title generation is off in protocol modes).
- Windows: `omp.exe acp` (Bun install, `C:\Users\johns\.bun\bin`) answered `initialize`, `session/new` and a prompt with a `C:\…` cwd; its `fs/read_text_file` carried `C:\…` paths. So the daemon starts `omp.exe` for PowerShell folders and `wsl.exe … omp acp` for WSL folders, mirroring the shell setting. OpenCode, Codex, Claude Code and Pi are installed on both sides here.
- Reusable, read in source: the kit's `TextViewState` (already behind Notes) appends streamed Markdown with `push_str`, keeps selection, opens links and highlights code blocks with tree-sitter; copy buttons need its `code_block_actions` hook, unused so far. The kit also has `MessageScroller` (a virtual list that follows the tail), `Message`/`Bubble` and a growing `TextareaState`. `DiffView` and `FileDiff` take any old/new text, but are reached only through Git scopes today. A daemon-owned agent copies the WSL Monitor collector (`system_metrics/wsl/source.rs`: piped `wsl.exe` child, reader thread, kill on drop); plain children are not in a job object, so the agent needs one to die with the daemon.
- Rust: `agent-client-protocol` 5.0.0 on crates.io (Apache-2.0, the ACP project's own SDK) has the typed schema. Phase 2 does not take it: the daemon's threads are synchronous and it uses a handful of methods, read with `serde_json::Value`.

Phase 2, basic chat (in source 2026-11-08, **protocol 38, workspace format 10**):

- Protocol: `compi_protocol::chat`. `PaneContent::Chat(ChatContent { id, harness, environment, folder, session })`; the transcript is `ChatState` (status Starting / Ready / Working since / Failed, model name, entries User / Agent / Thought / Tool / Error / Cancelled, a waiting `ChatPermission`), changed by `ChatEvent`s that `ChatState::apply` replays. `WatchChat` answers `ChatWatching` with the whole state, then sends `ChatChanged` on that connection; `SendChat`, `CancelChat`, `AnswerChatPermission`, `RestartChat` answer `ChatAccepted`. Format 10 stores a Chat leaf the way Monitor and Browser are, keeping its environment.
- Daemon (`chat.rs`): one `Chat` per chat ID, started by the first watch and ended by `ChatHub::retain` once no pane or view holds it (checked on each workspace change). It runs `omp.exe acp` for a Windows folder (search path, then `%USERPROFILE%\.bun\bin`) in a kill-on-close job, `wsl.exe --cd FOLDER --exec /bin/sh -c …` running the user's login shell for WSL, and the login shell on macOS; the login command adds `~/.local/bin` and `~/.bun/bin` to the end of the search path. It advertises no file system, terminal or form capabilities, so OMP does its own file work and its `ask` takes defaults until phase 3. Streamed chunks join the last entry of the same speaker; tool calls update their entry in place; a finished turn marks still-open tool calls Stopped. Exit code 127 or a missing program reads "OMP isn't installed …"; other exits show the last lines of standard error. A chat whose content carries a session resumes it with `session/load` (falling back to a new session with an inline error).
- Client (`gui/workspace/chat.rs`, `chat.rs`, `cli/chat.rs`): `compi chat` and the palette's **OMP chat** (`open_chat`) show a chat in place of the focused terminal's shell, in its folder and environment (beside it when that terminal already carries a chat). One watching connection per shown chat, sharing Monitor's watch plumbing (`WatchSlot`, `WatchLink`); actions go over a fresh connection off the UI thread. A window keeps each chat's model (state, one `TextViewState` per message, `MessageScroller`, the composer) while its pane or view exists, so Show Terminal keeps the draft and scroll. Header: OMP, the folder's last two names, the model. Messages are Markdown with code-block Copy (`code_block_actions`); tool calls are one row with a spinner, check, cross or stop mark; a permission is a row of the harness's choices; "Working · Ns" while a turn runs; Enter sends, Shift+Enter breaks a line, Stop cancels. A new session ID is written back into the pane (`UpdateContent`).
- Checked in `cargo dev` on Windows (posted keys and clicks): a WSL chat read a file, wrote `hello.py`, asked to run `python3 hello.py` (Allow once), and replied with a highlighted code block and Copy; closing the preview during `sleep 30` and reopening showed the same turn still working; Stop marked the call stopped and printed Stopped; Ctrl+Shift+E to the shell and back kept a typed draft; after `cargo dev --stop` and a fresh daemon the chat resumed its session with its history and answered about it, and no `omp acp` was left running; a PowerShell tab's chat ran `omp.exe` in `C:\…` with its own default model. 4. **Scrolling in TUIs and omp.** Scrolling up while a program prints keeps snapping back to the bottom.
   - Causes, measured on a Mac in `cargo dev`: scrollback is capped by 1 MiB of cell memory (`MAX_SCROLLBACK_BYTES`, about 33 bytes a cell), not the 10,000-line setting, so an 80-column pane keeps 420 of 3,000 printed lines and wider panes fewer. Once full, every new line evicts the oldest, the client sees a history that no longer starts with its old one and resets to the bottom (`gui/workspace.rs` `history_invalidated`). omp and Pi clear and reprint the scrollback (`ESC[2J ESC[H ESC[3J`) whenever something above the screen changes, which does the same. Each scrollback change resends the whole history (`terminal/mod.rs`, `Delta.scrollback`). In the alternate screen without mouse reporting (`less`, `man`, Git's pager) the wheel does nothing, and every trackpad event moves at least a line or sends a whole wheel click, with fractions never added up.
   - **Step 1, done in source for 0.2.1; no protocol-version change.** Text-and-neighbour anchors keep the reading row through eviction and clear/reprint, ignoring style changes. Split clear/reprint frames retain only the reading viewport for a 250 ms grace period; a real clear then returns to live output. Uncertain selections are cleared. A "↓ N new lines" chip returns to the bottom when clicked; typing does too. Per-pane fractional deltas produce only whole local scroll lines, mouse reports or alternate-screen arrows. DECSET 1007 defaults on in the daemon; an optional, backward-compatible JSON Input marker distinguishes synthesized arrows from real keys without changing the binary screen layout. Physical wheel/trackpad and Windows/WSL qualification are still open.
   - **Done in source 2026-10-20, step 2 (protocol 30).** History rows are kept compactly on both sides (`HistoryRow`: text, per-cell lengths only for wide or multi-byte cells, style runs, trailing blanks dropped). Deltas carry `Append { evicted, rows }`, or `Replace` on a real clear, RIS, a column resize that rewraps or a burst larger than the history; the client follows appends arithmetically and expands only rows it shows. The 1 MiB cap is replaced by `scrollback_lines × 512` bytes, measured at 10,000 lines × 80 columns: plain text 1.6 MB, colored output 3.2 MB, wide CJK 5.1 MB, all 10,000 lines kept. One appended line now costs 80–280 bytes of history on the wire instead of the whole history (about 11 MB at 10,000 lines before). In `cargo dev`, 12,000 printed lines left lines 1,979–12,000 in the pane (10,000 history plus the screen) where about 420 survived before. RIS now keeps the configured limits. Selection, links across wrapped rows, capture (byte-identical, tested against full rows) and the viewport fingerprint read compact rows.

### Program status (OSC 7501), phases A and B — 2026-10-12

- Specification: [Program Status Protocol](https://www.superlogical.com/rex/docs/build/program-status), revision 0.4.
- Daemon engine (`terminal/program_status.rs`):
  - The parser checks every limit before decoding: 4096-byte sequence, 16-byte keys, `msg` 2732 encoded / 2048 decoded, `title` 256 / 192, `app` 32, `id` 128 bytes, 32 per segment, 8 deep. A sequence that reached vte's 16-parameter cap is discarded, since it may have lost bytes.
  - Malformed pairs are skipped; bad base64, invalid UTF-8 or a control character discards the report; unknown keys are ignored; an unknown state or invalid `id` ignores it. `kind` applies only to `blocked`, `progress` only to `working` and `blocked`.
  - `ProgramStatusSet`: one record per `id`, each report replacing its record, `clear` removing a subtree or everything, 64 records with the least recently updated evicted, a generation that changes only with the records.
  - `OSC 7501;?` is answered with the supported states and kinds, ended like the query. OSC 133 `A` and process exit drop `idle`, `working` and `blocked`; `done` and `error` stay. RIS clears the records and keeps their generation counting; DECSTR and screen switches leave them.
  - The pre-parser now tracks OSC strings: over 4096 bytes for `7501;` or the largest OSC 52 payload otherwise, vte is reset and the rest is skipped to its terminator. An OSC ended by ESC followed by an APC no longer swallows the text after it.
- Daemon transport (`program_status.rs`, protocol 26):
  - Surfaces publish their records to a hub under the state lock. `WatchProgramStatus` sends each terminal's current status as `ProgramStatusChanged`, then `ProgramStatusWatching`, then the latest records of changed terminals at most every 100 ms; a client behind on reading gets them in a later round. `AcknowledgeProgramStatus` removes `done` and `error`.
  - Records go when the runtime is retired; watching connections retire closed panes on each workspace revision.
  - `DaemonClient` keeps the watched status in a cache (`watch_program_status`, `program_status`, `acknowledge_program_status`).
- Shell bridge: `compi-shell.sh` prints OSC 133 `A` at each prompt.
- Client:
  - `program_status.rs` (pure): headline urgency, app inheritance from the nearest ancestor, hover lines, removal of invisible and direction-changing characters, 160-character messages.
  - `gui/workspace/program_status.rs`: one watching connection per window, released while an update holds the window and replaced after a disconnect; static glyphs (no repaint), a 6 px dot in a tiled pane's top band, the glyph and progress in floating title strips, the state first in the sidebar and palette status line; hover names each pane and its records. A key or typed text in a pane removes its finished results at once and acknowledges them.
  - `[program_status] tabs`, `panes`, `sidebar` (default true) under Settings → Interface → Program status.
  - `compi --json pane list/show` adds `program_status`.
- Verification:
  - Unit tests for the parser limits and rules, the record set, the hub's coalescing and retry, the OSC cap, the presentation rules and the new settings.
  - `daemon_integration` `program_status_reaches_watchers_through_the_pty_and_follows_its_lifecycle` through ConPTY and WSL Bash: the feature-detection reply reaches the program, the bridge's prompt clears `working`, blocked → working → done in order with kind, message and progress, a later client gets the current record, acknowledgement clears it, exit keeps only the error, and closing the tab removes it on a connection that never reads the workspace.
  - Windows `cargo dev` with window captures: the blocked glyph on a background tab, tab and pane hover cards, Ctrl-C to a new prompt clearing blocked and working, `done` kept through clicks and focus changes and cleared by one key, a floating pane at 65%, status back after a preview restart, and the sidebar status line.
  - Not exercised: the Settings rows on screen, real reporting programs (Claude Code, Pi), macOS and its Unix integration twin, SSH.

### Stage, commit, discard (phase 6a) — 2026-10-12

- Protocol 24: `GitWrite { environment, repo, action }` returns `GitWritten { result }`. The actions:

- Hunk staging is line-ending safe:

## Completed: Phase 3 — durable workspace ownership

### Implemented

- Protocol v8 introduces distinct server, generation, session, tab, pane, surface, process-lifetime, mutation, and attachment identities. Terminal controls and screen frames carry enough identity to reject traffic from stale attachments or restarted processes.
- A single-writer workspace actor serializes mutations and runtime observations through bounded queues. It validates server generation and expected revision, fingerprints mutation content with SHA-256, retains a bounded durable receipt history, persists before publication and acknowledgement, and schedules process effects only after durable intent.
- The versioned `workspace-v1.json` store atomically replaces durable state. Legacy v1/v2 shell records migrate once into an imported session with one tab/pane/surface per record while retaining an exact backup. Interrupted migration reuses an identical backup; malformed current metadata is quarantined with a visible recovery message; active records reopen as `Lost`.
- Stable surfaces now have a fresh process lifetime for every launch attempt and a fresh attachment identity for every controller. Restart preserves the surface ID, rejects old-lifetime attachment and terminal traffic, and resets terminal state through a fresh authoritative snapshot.
- Session/tab/pane removal persists `Ending` intent before process cleanup and removes structure only after cleanup succeeds. Cleanup failure retains the affected structure and error for explicit recovery.
- The daemon, typed client, diagnostic probe, Windows console, and existing GPUI surface integration use the new workspace protocol. Ordinary client launch initializes only a never-initialized workspace; intentionally empty or lost workspaces do not create shells implicitly. Full hierarchy presentation remains Phase 4.

## Phase 4 — workspace client implemented

### Agreed UI direction — 2026-09-07

- **Primary:** Ghostty-like top terminal tabs. Each tab opens one terminal or its complete split layout, not an entire workspace. Creating, switching, reordering, and hiding tabs must work without opening the sidebar.
- **User-facing hierarchy:** Workspace → Terminal tabs → Panes. A named UI workspace maps to the existing server `Session`; the server's `Workspace` root remains the collection of all such groups. Do not introduce a separate session navigation layer or rename the protocol/persistence model for UI terminology.
- **Secondary:** a full Superterminal-style sidebar for browsing expandable workspaces and their tabs, organizing work, and finding/restoring hidden work. It supplements the top tab bar; it never replaces it. Every new or relaunched window starts with the sidebar closed, including tear-off windows. Remember width, not open visibility; expose a quiet chrome toggle, shortcut, and palette command, with no permanent rail, large selector, or reserved width when hidden. Reconnect, workspace switching, and tab creation/transfer never open it automatically.
- **Native windows:** dragging a terminal tab outside its window creates a new window containing that same tab and all its splits. Dropping onto another window transfers the tab there. Preserve workspace membership (server `Session`), surface identities, process lifetimes, contents, and valid focus/viewport state; never clone or respawn work.
- **Safe transfer:** keep the source attached during the drag; Escape cancels without moving anything. Accept a drop through an explicit attachment handoff, never concurrent controllers or PTY resize fights. Failed window creation/attachment keeps or restores the source view with a visible error. Moving the last tab leaves an empty source window, not a replacement shell.
- **Presentation ownership:** existing destination windows keep their own appearance overrides, zoom, and sidebar state. A new tear-off window inherits the source's resolved theme, opacity, background effect, zoom, and sidebar width but starts with its sidebar closed. Global appearance defaults live in TOML; private JSON stores only explicitly changed window fields; CLI theme overrides remain invocation-only.
- **Dark Glass and themes:** Dark Glass remains the default with neutral-dark surfaces, acid-green accent, and restrained native materials. Warm Carbon remains the coordinated alternative. Quick Appearance and Settings expose both presets plus 10–100% terminal opacity and clear/blurred native backgrounds, with readable opaque/reduced-transparency fallbacks.
- These decisions replace the earlier sidebar-first and opaque-terminal-only presentation plans.
